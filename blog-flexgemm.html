FlexGEMM — CPU Fallback

Cross-Platform Backend for High-Performance Sparse 3D Convolutions

🕒 8 min read View on GitHub (Fork)
Python Triton Sparse Convolutions PyTorch CPU Kernels

Overview

FlexGEMM is a Triton-powered GEMM backend specifically designed for 3D sparse convolutions used in voxel-based neural networks. The original project (by JeffreyXiang) achieves ~2x speedup over existing solutions like spconv and torchsparse on FP16 and TF32 precision, tested on NVIDIA A100 80GB PCIe.

My contribution focuses on extending coverage to CPU hardware — specifically writing CPU fallback implementations for the core coordinate-building CUDA kernels so FlexGEMM can operate on hardware with limited or no GPU memory. This work was motivated by hitting VRAM bottlenecks while running TRELLIS 2 (a 3D generation model that depends on sparse convolutions).

The Problem

3D sparse convolutions operate on voxel grids where most cells are empty. The key computational challenge isn't the convolution itself — it's building the coordinate maps that tell the kernel which input voxels map to which output voxels. The original FlexGEMM implements these as CUDA kernels:

  • hashmap_build_sparse_conv_out_coords — Builds output coordinate arrays for regular sparse convolutions using hash maps
  • expand_unique_build_sparse_conv_out_coords — Expands and deduplicates output coordinates
  • hashmap_build_submanifold_conv_neighbour_map — Builds neighbour maps for submanifold convolutions (where input and output coordinates are identical)

When GPU VRAM is exhausted (common with large 3D models on consumer hardware), there's no fallback — the entire pipeline fails. My work provides CPU-native implementations so these operations can complete, albeit at reduced speed.

Implementation

Completed Kernels

hashmap_build_sparse_conv_out_coords — CPU-native implementation tested and verified for correctness. Translates the CUDA hash-map-based coordinate building to CPU using Python dictionaries and NumPy operations. The key challenge was maintaining the same hash-collision handling semantics as the GPU version.

expand_unique_build_sparse_conv_out_coords — CPU-native implementation tested and verified for correctness. Handles the expansion of coordinate sets with deduplication, critical for ensuring output coordinates are unique before convolution.

In Progress

hashmap_build_submanifold_conv_neighbour_map — Currently functional but requires optimization. The CPU path is ~10x slower than the GPU path; the initial implementation prioritized correctness over performance. The bottleneck is poor performance of PyTorch CPU ops like masked_select when operating on large sparse tensors.

Key Technologies

  • Triton kernel language — The GPU kernels are written in Triton, a Python-like DSL for GPU programming. Understanding Triton was essential for writing correct CPU equivalents.
  • PyTorch sparse tensor operations — COO/CSC sparse formats for representing voxel coordinates and neighbour relationships.
  • Split-K parallelism — Used in the GPU path for large convolutions; the CPU path uses different parallelization strategies.
  • Map/coordinate building — The fundamental operation: given input coordinates and a kernel size, determine which output coordinates exist and how they map.

Challenges & Trade-offs

The fundamental tension in CPU fallback design is correctness vs. performance. The GPU kernels are highly optimized for parallel execution — hash maps with atomic operations, warp-level primitives, and memory coalescing. Translating these to CPU requires different algorithms entirely:

  • GPU hash maps → Python dictionaries (correct but slow)
  • Warp-level atomics → Sequential operations with locks
  • Memory-coalesced access → Cache-friendly but different access patterns

The masked_select bottleneck on the CPU path is a known PyTorch limitation. I've raised this with the FlexGEMM maintainers to discuss architectural integration approaches for a maintained CPU execution path. Potential solutions include replacing masked_select with boolean indexing or implementing custom C++ extensions.

Status & Next Steps

Two of three kernels are complete and verified. The submanifold convolution neighbour map is functional but needs optimization. The long-term goal is to integrate the CPU path into FlexGEMM's main codebase as a first-class fallback, enabling 3D sparse convolution models to run on CPU-only hardware (laptops, edge devices, cloud instances without GPUs).

This work directly enables running models like TRELLIS 2 on consumer hardware where VRAM is the limiting factor, democratizing access to 3D generation research.

FlexGEMM: CPU fallback

Native C++ kernels for sparse 3D convolution on machines without enough GPU memory

7 min read · Oct 2026 Fork on GitHub
C++17OpenMPPyTorchTritonsparse convolution

The problem

FlexGEMM, by JeffreyXiang, is a Triton GEMM backend for the 3D sparse convolutions used in voxel networks. The upstream project reports about 2× the speed of spconv and torchsparse on FP16 and TF32 on an A100 80 GB PCIe.

I ran into it while running TRELLIS 2, which ran out of VRAM on my hardware. A sparse convolution first has to work out which output voxels exist, and in FlexGEMM that step is a CUDA kernel. With no GPU memory to spare there was nothing to fall back on, so the whole pipeline stopped. My branch adds CPU implementations of those coordinate-building kernels.

Of the three coordinate-building steps, two now have native CPU kernels. The third, the submanifold neighbour map, still goes through a PyTorch fallback.

What I built

The work is on the cpu-support branch of my fork (issue #30, PR #29). It adds a C++17 extension compiled with OpenMP, exposing hashmap_build_sparse_conv_out_coords and expand_unique_build_sparse_conv_out_coords, and wires them into SparseConv3dFunction whenever the coordinates live on the CPU. It also includes CPU versions of the Z-order and Hilbert serialisations and a Bloom filter.

The first version, from early July, was correct and very slow. Profiling it showed that masked_select and unique dominated, so the rest of the work went into those.

Bucket dispatcher instead of atomics

The GPU kernel inserts into one shared hash map with atomics. On the CPU that would put every thread on the same few cache lines. Instead the hash map is split into segments and a BucketDispatcher lets each thread lock one segment and work on it with no further synchronisation. Each lock is a PaddedLock, aligned to the cache line, so neighbouring locks do not false-share.

It is the same rule I used in Threadweaver: values that different cores write must not share a cache line. A thread-per-bucket lock replaces the per-insert atomic.

Replacing masked_select

torch::masked_select turned out to be very slow on the CPU for this workload. I wrote a CPU-specific replacement that removes the sentinel entries the kernel leaves behind. It reuses the bucket dispatcher: the input is divided into ranges whose output offsets are known in advance, each thread locks a range and copies the entries it keeps into that range's own part of the output, and the copy itself is branch-free. That commit made the kernel more than 60% faster in my profiling.

Results

I checked the output of each kernel against the library's pure-PyTorch reference for output coordinates, using sphere-shaped voxel sets at resolutions 16, 32 and 64, with three convolution configurations (3×3×3 stride 1 pad 1, 3×3×3 with dilation and padding 2, and 2×2×2 stride 2). The outputs were identical in every case. Each figure is the median of three runs on an 8-thread laptop CPU (Ryzen 7 6800H).

The baseline is the pure-PyTorch CPU reference path, not the GPU kernel, and the inputs are synthetic spheres. It shows the native kernels are far better than the reference on the CPU, not that they match a GPU.

What is left

  • A native CPU kernel for the submanifold neighbour map, which currently uses a PyTorch fallback.
  • Benchmarks on real TRELLIS 2 inputs, not just synthetic spheres.
  • Continuing the conversation with the maintainers about how a maintained CPU path should be structured and tested in the library.

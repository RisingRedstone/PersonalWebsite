Matching Engine Threadweaver

Three ring-buffer protocols for a low-latency matching engine, and an honest status report

8 min read · Oct 2026 Source on GitHub
C++23lock-freeMPSCcmovNixcallgrind

Where it stands

The goal is a matching engine for high-frequency workloads, in C++23, built hardware-first. So far I have built and benchmarked the layer underneath it: the messaging between processes and the shared-memory allocators, plus an early skip list. The matching logic itself is not written yet.

The 1.25B and 650M ops/sec figures in this post measure the ring buffers. They are the foundation of the engine, not an end-to-end order-matching rate.

Three protocols

One engine needs different queues for different traffic. A single producer feeding a single consumer should pay almost nothing. Many producers feeding one consumer must not serialise on one shared counter. I built a protocol for each.

ProtocolShared stateBest for
SimpleOne atomic head per directionOne producer, one consumer
Three-pointerwrite_head, commit_head, read_head, each on its own lineSeveral producers, one consumer
Cell-lockableTwo heads, plus a lock bit in every cellHeavy multi-producer contention

Simple

Each side keeps a cached copy of its own head and loads the other's with acquire semantics. A write fails when w_h >= size + r_h. There is also a branchless variant that uses inline x86 cmov to pick pointers, so a rarely-taken condition does not cost a pipeline flush. The Threadweaver post walks through this one with an animation.

Three-pointer

Producers claim a slot by CAS on write_head, write their data, then publish by CAS on commit_head. The consumer only reads commit_head. Keeping those two on separate cache lines means a producer's claim does not disturb the line the consumer polls. Producers still wait for each other at commit_head, and that is the bottleneck the next protocol removes.

Cell-lockable

There is no commit_head. A producer takes a slot with fetch_add on write_head, then spin-locks that one cell before writing. The lock is a single bit in a one-byte header, set with an inline lock bts, and an RAII guard releases it. Contention is spread over as many cells as the buffer has. The optimised variant uses _mm_pause() while spinning, caches the write head, and uses relaxed increments.

Benchmarks

ConfigurationThroughput
1 producer, 1 consumer1.25B ops/sec
8 producers, 1 consumer650M ops/sec

In the benchmark processes the producer and consumer are pinned to separate cores, and the harness counts cycles with rdtscp. Profiling used callgrind with cache simulation and instruction dumps, viewed in kcachegrind.

Design decisions

  1. Cell-lockable for scaling. Serialising producers on one commit counter does not survive heavy contention, so the lock moves into the cells. At 8×8 threads this was about 3× faster than the naive baselines.
  2. 64-byte granularity everywhere. Heads are a full line apart, and containers are packed to exactly one line, checked with static_assert.
  3. No mutexes. Every synchronisation point is an atomic: compare_exchange_weak, fetch_add, or a test-and-set on a lock bit.
  4. Mistakes fail the build. Capacity, index types and guard types are checked by concepts, so a wrong combination does not compile.
  5. Huge pages. Buffers are mapped with 2 MB pages to keep the TLB from becoming the limit at large sizes.

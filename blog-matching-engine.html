Matching Engine (Threadweaver)

A low-latency matching engine in C++23, and Threadweaver, the lock-free messaging layer I built first

11 min read · Oct 2026 Source on GitHub
C++23lock-freeatomicsMPSChuge pagescmovcallgrindLTTng

Where it stands

The goal is a matching engine for high-frequency workloads, in C++23, built hardware-first. I am building it bottom-up, and Threadweaver is the name of the first layer: the messaging between processes, the shared-memory allocators under it, and the cache-line-aware containers both are made of. It lives in the same repository as the engine.

Ring buffers (simple, three-pointer, cell-lockable)Built and benchmarked

The 1.25B and 400M ops/sec figures below measure the ring buffers. They are the foundation of the engine, not an end-to-end order-matching rate.

The problem

Moving a value from one core to another is not limited by arithmetic. It is limited by the cache-coherence protocol: every time two cores touch the same cache line, that line has to travel between them. A queue between two processes is a good test of that, because the only work is handing data over.

Threadweaver is my attempt to see how close a queue can get to that hardware limit, because an engine that matches orders across processes spends much of its time handing data over.

Design

Layout: one cache line per hot value

The first rule is that independently written values never share a 64-byte cache line. In the ring buffer layout, write_head and read_head are each alignas(64), so the producer writing one head does not invalidate the line the consumer is reading the other from. Data containers follow the same rule: CacheLineSlot<D, Header> is checked with static_assert to be exactly 64 bytes, and CacheLinePacked is a union that exposes the same line as raw uint64_t[] for copying or as a typed slot for use.

The second rule is that capacity is a power of two, so the slot for a head is head & (size - 1) and not a division. Heads only ever grow, which also removes the need to distinguish "full" from "empty" with a spare slot: the buffer is full when w_h >= size + r_h.

Each side caches its own head and only loads the other side's head. The one cross-core load per call is the cost of knowing whether the buffer is full or empty. Everything else stays in the core's own cache.

Three protocols for different traffic

One engine needs different queues for different traffic. A single producer feeding a single consumer should pay almost nothing. Many producers feeding one consumer must not serialise on one shared counter. I built a protocol for each.

ProtocolShared stateBest for
SimpleOne atomic head per directionOne producer, one consumer
Three-pointerwrite_head, commit_head, read_head, each on its own lineSeveral producers, one consumer
Cell-lockableTwo heads, plus a lock bit in every cellHeavy multi-producer contention

Simple: one producer, one consumer

Each side keeps a cached copy of its own head and loads the other's with acquire semantics. There is also a branchless variant that uses inline x86 cmov to pick pointers, so a rarely-taken condition does not cost a pipeline flush. This is the design behind the 1.25B ops/sec figure. The producer and the consumer are separate fork()ed processes pinned to CPUs 3 and 2, which are the two hardware threads of one physical core, so they share an L1 cache. They use one mmap'd layout.

  • Full: when w_h_cache >= size + r_h, write() returns false and the caller retries. In the benchmark the retry loop only issues pause after 100 failed attempts.
  • Empty: when r_h_cache >= w_h, read() returns nullopt and the consumer retries the same way.
  • Wrap-around: because the slot is head & (size - 1), any size that is not a power of two would silently break indexing, which is why the PowerOfTwo concept rejects it at compile time.

Three-pointer

Producers claim a slot by CAS on write_head, write their data, then publish by CAS on commit_head. The consumer only reads commit_head. Keeping those two on separate cache lines means a producer's claim does not disturb the line the consumer polls. Producers still wait for each other at commit_head, and that is the bottleneck the next protocol removes.

Cell-lockable

There is no commit_head. A producer takes a slot with fetch_add on write_head, then spin-locks that one cell before writing. The lock is a single bit in a one-byte header, set with an inline lock bts, and an RAII guard releases it. Contention is spread over as many cells as the buffer has. The optimised variant uses _mm_pause() while spinning, caches the write head, and uses relaxed increments.

Shared memory without copies

Buffers live in memory mapped with mmap(MAP_SHARED | MAP_ANON | MAP_HUGE_2MB) before the fork(), so every child sees the same pages. Huge pages cut down the number of TLB entries a large buffer needs, which matters once the buffer is bigger than the TLB can cover with 4 KB pages.

Two allocators sit on top. OneTimeStaticSharedMemoryAllocator is reference-counted and records the owner PID, so a forked child cannot unmap memory its parent still uses. DistributedDynamicParentAllocator manages named segments through shm_open/shm_unlink in a 100-entry table, and can grow a segment with mremap(MREMAP_MAYMOVE).

Compile-time contracts

Most of the dangerous mistakes in this code (wrong size, wrong index type, a lock guard used with the wrong layout) are silent at runtime, so I moved them into C++20 concepts that fail the build instead.

Concepts used
  • PowerOfTwo<N> enforces power-of-two capacity for mask indexing.
  • IsStandardUint<T> limits index types to uint8_t through uint64_t.
  • LockableCell<T> requires try_lock, unlock, clear_data and contains_data.
  • ReadLockableIndex<Layout> and WriteLockableIndex<Layout> check that a layout's guard types are movable but not copyable.
  • LayoutVerification<T> checks that a layout exposes MemLayout, data_type, index_type, atomic heads and operator[].
RAII guard hierarchy
  1. SingleResourceLockGuard: stateless unlock functor.
  2. InstSingleResourceLockGuard: stores the unlock object, for unlock logic that needs context.
  3. InstSingleResourceLockGuardWrapper: chains several unlock behaviours.
  4. TemplateLockedLockGuard: type-state locking, where locking turns a T<false> into a T<true>.

Measurements

ConfigurationThroughputSetup
1 producer, 1 consumer (SCSP), simple buffer1.25B ops/secTwo processes pinned to the two hardware threads of one physical core (sharing L1)
8 producers, 1 consumer (SCMP)400M ops/secMulti-producer protocol under write contention

The 1.25B figure depends on that topology: with the producer and consumer on one core's L1, the head the other side polls never has to cross cores. Both numbers come from the repository's benchmark harness, which forks the reader and the writers, pins them, and times the transfer with rdtscp. Per-function instruction counts came from callgrind and call-graph inspection in kcachegrind; execution tracing used LTTng-UST with URCU for safe reclamation.

These are microbenchmarks of the queue itself, in one environment. They say how fast data can move through the buffer, not how fast an application built on top will run.

What went wrong and what I would change

  • My first memory orderings were wrong. An early commit message of mine says I had used whatever order compiled. I went back through every load and store and chose each one on purpose. In the cell-lockable design the cell's own lock already gives the acquire and release, so the head accesses there can be relaxed.
  • Several bugs lived in the type system, not the algorithm. An unlock type in the guard hierarchy was declared against the wrong name. That is the kind of mistake the concepts now catch at compile time.
  • Contention moves, it does not vanish. The three-pointer protocol serialises producers on commit_head. The cell-lockable protocol spreads that over the cells, and in my 8-thread contention test it came out about 3× faster than the naive baselines.
  • What I would do next: record the full benchmark environment alongside every number, and measure the same buffers with the two processes on different physical cores, to see how much of 1.25B is topology.

What comes next

The order book is next: a skip list whose nodes carry aggregates (order counts, price maxima) so the hot path can defer inserts and deletes. After that comes the matching logic itself, fed by these buffers.
